# 云生变更管理

让“为什么改、改了什么、谁批准、影响多大”全部可回溯，避免在版本、工期和成本之间失去因果关系。

## 适用

- Brief 已进入审核或已 Approved，又出现新卖点、新渠道、规格、交期、素材或创意调整。
- 脚本、分镜、静帧、动态、声音或成片间需要维护版本链。
- 更换模型、参数或制作路径，且可能影响质量、工时、算力、工期或合规。
- 需要区分原范围内缺陷修正与新范围。

## 不适用

- 尚无可引用的需求卡、Brief 或交付版本基线。
- 只是整理审核意见，尚未形成实质范围变动。
- 用于删除历史版本、覆盖原始证据或追认一个从未发生的批准。

## 输入

- `project_id`、当前有效基线及完整版本号。
- 变更请求原文、发起人、时间、理由和期望结果。
- 当前制作阶段、任务状态、已产生素材、工时、算力和交期。
- 范围、费用、时间、品牌、法务、数据安全等各类决策人。

## 强约束

- 变更记录必须指向一个不可被覆盖的基线版本与一个原始 `source_id`。
- 先评估、后决策、再生成新版本。未获批准时不更改有效基线。
- 区分“缺陷修正”、“原范围内调整”、“新范围”和“外部强制变更”。类型不能由执行者为规避成本影响而改写。
- 工时、算力、金额、交期和交付数量必须附数值/单位、周期、对象、口径、来源及已核验/推算/待补证状态。
- 评估不充分时输出区间和前提，不给出伪精确值。不将市场报价当作内部实际成本。
- 保留 Brief、脚本、分镜、Prompt、静帧、动态和成片之间的父子关系，不删除历史记录。

## 事实契约

- 缺失不等于 0。“未提供”、“无法核验”和真实的数值 0 必须分开。
- 所有定量信息按“事实 / 推算 / 估算 / 外部基准”分栏，不得混写；外部基准另附发布日期与适用条件。
- 数字必须附周期、范围、单位、分母或公式及 `source_id`；无 `source_id` 时仅能记为待补证。
- 来源等级与计算方式分开记录：`source_grade` 中 A=系统/账单/正式记录，B=带日期可复核截图或人工台账，C=用户陈述，D=外部基准，N=无证据；`claim_method` 使用 direct/derived/estimated/benchmark/unknown。
- 本 Skill 生成的变更单默认为 Draft，不会自动获得对外使用批准；对外引用、发送或发布前必须人工确认。

## 工作流

1. 验证项目、当前有效基线、变更来源和发起人。
2. 逐字段列出 Before/After，区分新增、删除、替换和仅表述澄清。
3. 对变更进行分类，并检查它是否超出原范围、是否与已有决策冲突。
4. 评估对交付物、任务依赖、已完成工作、活动工时、算力、等待时间、交期、质量和合规的影响。
5. 生成“接受、拒绝、改期、降范围”等选项及各自代价，由相应决策人选择。
6. 获得明确决策后，创建 `change_id`、新版本号、受影响任务和已通知人员清单。
7. 更新变更台账和版本系谱，保留原基线、评估与批准证据。

## 固定输出字段

1. `change_id`、`project_id`、发起人、发起时间、`source_id`。
2. 基线类型与基线版本，变更类型与业务原因。
3. Before/After 差异表及受影响交付物。
4. 影响表：范围、工时、算力、工期、质量、品牌/合规和已完成工作。
5. 可选处理方案、交换条件与建议。
6. 决策、决策人、时间、批准证据和生效时间。
7. 新版本号、版本系谱、受影响任务、责任人和通知清单。
8. 数据缺口、估算假设和证据状态。

## 停止与人工确认

- 无法确定有效基线、变更来源或最终决策人时，不生成新版本。
- 变更影响预算、工期、交付数量、主创意、品牌、版权、隐私或数据安全时，必须获得对应负责人确认。
- 无法对影响做出可核验估算时，先列出补证或 POC 计划，不对成本与时间做承诺。
- 任何覆盖、删除或伪造历史记录的请求都应停止。
