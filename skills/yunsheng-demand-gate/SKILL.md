# 云生需求闸机

把未结构化的消息变成一张“能否进入 Brief”的可审核需求卡。保留原始证据，不替需求方做未授权的决策。

## 适用

- 从飞书、微信、企微、邮件、会议纪要或口述中收口视频需求。
- 识别业务目标、交付物、时间、硬性约束、决策和冲突。
- 判断需求是否足以进入创意 Brief，并生成最少量的确认问题。

## 不适用

- 需求已确认，只需写创意 Brief、脚本、分镜或 Prompt。
- 评审已有 Brief，或统计制作工时、算力与 ROI。
- 需要直接读取用户未提供、未授权的内部聊天记录。

## 输入

优先获取：

- 原始消息或导出文件，包含发言人、时间和消息顺序。
- 业务线、需求发起人、决策人和交付对象。
- 已知的截止时间、渠道、规格、素材、预算、品牌及合规约束。
- 可选的项目编号和既有需求卡，用于去重或关联。

输入不全时先处理已有证据，不得用常识补成内部事实。

## 强约束

- 每条事实、决策或约束都标注 `source_id`；无原文支持的内容标记为“推断”或“待确认”。
- 区分“已决定”、“偏好”、“建议”和“待办”，不得互换。
- 人物、时间、预算、数量、播放量等内部数字一律记录：数值/单位、周期、统计对象、分母或公式、来源与状态（已核验/推算/待补证）。
- 不用外部行业均值代替内部实际数据，不编造交付量、成本、提效或验收结果。
- 对外版本必须脱敏；脱敏不得改变时间范围、指标口径或因果关系。

## 事实契约

- 缺失不等于 0。“未提供”、“无法核验”和真实的数值 0 必须分开。
- 所有定量信息按“事实 / 推算 / 估算 / 外部基准”分栏，不得混写；外部基准另附发布日期与适用条件。
- 数字必须附周期、范围、单位、分母或公式及 `source_id`；无 `source_id` 时仅能记为待补证。
- 来源等级与计算方式分开记录：`source_grade` 中 A=系统/账单/正式记录，B=带日期可复核截图或人工台账，C=用户陈述，D=外部基准，N=无证据；`claim_method` 使用 direct/derived/estimated/benchmark/unknown。
- 本 Skill 生成的内容默认为 Draft，不会自动获得对外使用批准；对外引用、发送或发布前必须人工确认。

## 工作流

1. 为每份输入分配 `source_id`，保留发言人、时间和原文位置。
2. 把消息拆成原子信息，分类为事实、目标、约束、决策、偏好、待办和风险。
3. 合并重复内容，保留相反说法，标出冲突的发起人与时间。
4. 归纳业务问题、目标受众、期望行动、交付物、规格、截止时间、硬性限制和非目标。
5. 把缺口分成“阻塞 Brief”和“可在 Brief 中继续澄清”，仅询问会改变范围或方向的问题。
6. 给出 `Ready for Brief: Yes/No`及证据。判定为 Yes 前，必须至少明确业务目标、主要受众、核心交付物、最终决策人和硬性时间/合规约束。
7. 请需求发起人或授权决策人确认需求卡；确认前不将推断升级为事实。

## 固定输出字段

1. `request_id`、创建时间、业务线、需求发起人、决策人。
2. 来源索引：`source_id | 来源 | 发言人 | 时间 | 位置`。
3. 已确认事实与原文证据。
4. 业务问题、目标受众、期望行动和成功信号。
5. 交付物、规格、时间、资源、品牌/IP/合规约束和非目标。
6. 已决定项、偏好项、冲突项、推断项和待补证项。
7. 阻塞问题及责任人。
8. `Ready for Brief`判定、理由与下一步。

## 停止与人工确认

出现以下任一情况时停在需求卡，不进入 Brief：

- 业务目标、交付物或最终决策人不明。
- 重大冲突无授权人裁决。
- 截止时间、品牌、版权、肖像、隐私或安全条件可能改变方案。
- 需要访问未授权的内部系统或个人数据。

仅由需求发起人或明确授权的决策人确认需求卡。
